# Сбор точных данных по медленным запросам (Chrome / Edge DevTools)

Цель: по скринам/HAR понять, где теряется время — **до старта запроса**, в **очереди**, **DNS/TCP/TLS**, **TTFB**, **скачивании**, **waterfall/зависимостях**, **дубликатах fetch**.

Приоритетные маршруты (если тормозят):

- `GET /api/v1/tasks?platform=twitch` (и при необходимости `kick` / `all`)
- `GET /api/v1/shop/items?platform=twitch|kick`
- Любой запрос с именем **config** в списке (часто это `GET /api/v1/games/fortune/config` — см. колонку **Name** / URL)
- `GET /api/v1/games/fortune/state`, если долгий

Если медленный только один route — достаточно **его**. Если несколько — лучше **по каждому** отдельный набор материалов.

---

## 1. Подготовка

1. Открыть сайт в **Chrome** или **Edge**.
2. **DevTools** → вкладка **Network**.
3. Включить:
   - **Preserve log** (сохранять лог при навигации).
   - **Disable cache** (для честного cold; для warm можно один раз снять с выключенным кэшем и повторить сценарий без reload — см. ниже).
4. **Очистить** список запросов (иконка 🚫).
5. Выполнить сценарий:
   - **Startup / после reload:** полный **reload** страницы (F5 / Ctrl+R).
   - **Экран Tasks / Shop:** после reload **отдельно перейти** на экран (табы/роут), не смешивать с первым paint, если нужен именно экранный запрос.
6. Дождаться появления медленного запроса в списке.

**Заметки:**

- Для сравнения **cold vs warm:** первый заход после reload — обычно **cold**; второй переход на тот же экран без полного reload — чаще **warm** (и/или повторный fetch при инвалидации).

---

## 2. Что открыть у каждого «подозрительного» запроса

### A. Вкладка **Headers**

Зафиксировать (текстом или скрин):

| Поле | Зачем |
|------|--------|
| **Request URL** | Точный путь + query (`platform=…`) |
| **Request Method** | GET/POST |
| **Status Code** | 200 / 401 / … |
| **Timing-Allow-Origin** | Если есть — полезно для CDN |
| **Cache-Control** / **Age** | Кэш браузера/CDN |
| **Content-Length** | Объём ответа (отличать TTFB от «тяжёлого тела») |
| **Server**, **Via**, **x-cache**, CDN-заголовки | Прокси/edge |
| **Authorization** | Наличие `Bearer` (токен можно замазать) |

### B. Вкладка **Timing** (обязательно)

Нужны **все фазы**, целиком:

- **Queueing**
- **Stalled**
- **DNS Lookup**
- **Initial connection**
- **SSL** (TLS)
- **Request sent**
- **Waiting for server response** (= **TTFB** с точки зрения браузера)
- **Content Download**

Идеально: **скрин всей вкладки Timing** или переписать значения вручную.

### C. Положение в **waterfall**

Нужен **общий вид** списка Network:

- Когда **стартовал** запрос относительно других (временная шкала).
- Не **блокируется** ли он предыдущими (очередь HTTP/2, лимиты домена).
- Нет ли **двух одинаковых** URL подряд (duplicate fetch).
- Нет ли каскада вида **me → state → tasks → items** (зависимость по времени старта).

---

## 3. Скриншоты (минимум на один медленный запрос)

| № | Что | Содержание |
|---|-----|------------|
| **1** | Общий **Network** | Waterfall, **Duration**, **Initiator**, видна шкала времени, соседние запросы |
| **2** | **Timing** выбранного запроса | Полностью, все фазы |
| **3** (опционально) | **Headers** этого же запроса | Как в п.2A |

Колонки в списке Network полезно включить: **Name**, **Status**, **Type**, **Initiator**, **Size**, **Time**, **Waterfall**.

---

## 4. HAR (опционально, но очень полезно)

1. Network → ПКМ по списку → **Save all as HAR with content** (или через меню «Export HAR»).
2. Перед экспортом: тот же сценарий (reload / переход на экран), **Preserve log** включён.
3. Прислать файл (можно архивом). По HAR можно восстановить точные тайминги без скринов.

**Внимание:** HAR может содержать **Authorization** и cookies — перед отправкой в публичный чат вырезать/замазать секреты или приложить только к приватному тикету.

---

## 5. Текстом к материалам (обязательно)

1. **Сценарий:** что делали (например: reload главной → открыл Tasks → переключил платформу на twitch).
2. **Контекст:**
   - залогинен: да/нет;
   - **TMA** (Telegram Mini App) или обычный браузер;
   - **cold** (первый запрос после reload / первый заход на экран) или **warm** (повтор).
3. **Какой route тормозил:** точный path + query (tasks / shop items / fortune config / state / другое).

---

## 6. Как читать типичные сценарии

### Сценарий A — запрос **стартовал поздно**, сервер **быстрый**

- В waterfall большой **разрыв** до начала полоски запроса.
- **Waiting for server response (TTFB)** относительно **небольшой**.

**Имеет смысл:** задержка на фронте (ожидание токена, роутера, React), лимит параллельных соединений, очередь.

### Сценарий B — запрос вовремя, **долго ждёт ответ сервера**

- Основное время в **Waiting for server response**.

**Имеет смысл:** backend, БД, Redis, логика маршрута, прокси до origin.

### Сценарий C — долго **соединение**

- Большие **DNS Lookup**, **Initial connection**, **SSL**.

**Имеет смысл:** сеть, холодный TCP/TLS, CDN/edge, географическая удалённость.

### Сценарий D — **дубликаты / каскад**

- Два одинаковых запроса к API.
- Второй стартует явно после завершения первого без необходимости.

**Имеет смысл:** дублирующий `useEffect`, смена query key, prefetch + mount, смена platform.

## 7. Формат отчёта (шаблон для вставки в тикет)

Скопировать и заполнить **на каждый** проблемный route.

```markdown
## Route
GET /api/v1/tasks?platform=twitch

## Сценарий
Reload → переход на экран Tasks

## Контекст
- logged in: yes
- TMA: yes / no
- cold / warm: cold

## Скрин 1
[waterfall Network — вставка или ссылка]

## Скрин 2
[Timing — вставка или ссылка]

## Скрин 3 (опционально)
[Headers — вставка или ссылка]

## Timing текстом (если удобнее)
- Queueing: … ms
- Stalled: … ms
- DNS: … ms
- Initial connection: … ms
- SSL: … ms
- Request sent: … ms
- Waiting for server response: … ms
- Content Download: … ms

## Дополнительно
- HAR: приложен / нет
```

---

## 8. Минимальный вариант (если мало времени)

1. Скрин **Network** с выделенным медленным запросом (видно waterfall + Initiator).
2. Скрин **Timing** этого запроса.
3. Подпись: **route**, **экран**, **cold/warm**, **logged in**, **TMA да/нет**.

Без **Timing** только по **Duration** классифицировать проблему нельзя.

---

## 9. Что не подходит как единственное доказательство

- Только тело JSON ответа.
- Только **Time** / Duration в списке **без** вкладки Timing.
- Только Lighthouse без разбора конкретного запроса в Network.

---

## 10. Связь с бэкендом

- **TTFB в браузере** близок к «сервер думает + сеть до origin», но не включает **Queueing/Stalled** на клиенте.
- Сравнение: тот же URL через `curl` на `127.0.0.1` у сервера vs публичный origin — помогает отделить **логику API** от **TLS/прокси** (см. `docs/dynamic-routes-performance.md`).
