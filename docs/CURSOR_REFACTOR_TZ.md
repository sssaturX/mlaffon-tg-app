# ТЗ для Cursor-агента: пошаговый рефакторинг HTTP/WS клиента

**Статус реализации (код):** фазы **A–F** внедрены (`liveBroadcastStore`, дедуп `refreshMe`, WS backoff, `balance_updated` no-op, условные `onRefresh` в Home/Tasks). Фаза **G** частично: Zustand только для эфира; перенос `me`/дропа в store — по необходимости отдельно.

**Назначение:** один файл с порядком работ, критериями готовности и ограничениями. Не дублирует полный аудит — перед фазами читай **[API_WEB_CLIENT_AUDIT.md](./API_WEB_CLIENT_AUDIT.md)** и **[REALTIME_ARCHITECTURE_PLAN.md](./REALTIME_ARCHITECTURE_PLAN.md)**.

**Область:** `apps/web`, при необходимости `apps/api` + `packages/shared` для контрактов.

**Правила для агента:**

- Делай **одну фазу за итерацию** (или подфазу), затем `npm run build -w web` (и `-w api`, если трогал API).
- **Не** расширяй scope:** только задачи фазы; без косметических рефакторингов «вокруг».
- Сохраняй **обратную совместимость API**, пока явно не сказано «удалить маршрут/поле».
- После изменений обнови **одну строку** в `API_WEB_CLIENT_AUDIT.md` (раздел частот/статуса), если поменялись интервалы или контракт WS.

## Фаза A — Эфир: меньше `GET /live-broadcast` (high impact)

**Цель:** при живом WebSocket не крутить опрос каждые 5 с, если состояние эфира можно взять из событий + редкий fallback.

**Шаги (по порядку):**

1. **API:** убедиться, что `live_started` / `live_ended` в Redis/WS содержат **достаточно данных** для UI (как минимум: `id`, `platform`, `streamUrl`, `startedAt`; для `live_ended` — явный сигнал сброса). Файлы: `apps/api/src/services/liveBroadcast.ts`, `realtimePublish.ts`, при необходимости типы в `realtimePublish` / клиент.
2. **Web:** поднять состояние «текущий эфир» в **React Context** (или тонкий store), которое:
  - инициализируется **одним** `GET /api/v1/live-broadcast` при входе на главную / mount;
  - обновляется из **WS** (`live_started` / `live_ended`) без немедленного GET;
  - при **reconnect** WS (см. хук) — **один** `GET` для синхронизации.
3. **Home.tsx:** ослабить интервал:
  - при `live.active === false` оставить редкий тик (например 20–60 с) **только если** нет WS или после ошибки;
  - при `live.active === true` и подключённом WS — **убрать** агрессивный 5 s poll или заменить на 30–60 s safety-net.
4. Сохранить `CustomEvent("mlaffon-live")` или заменить на обновление контекста — без поломки подписчиков.

**Критерии приёмки:**

- На главной при стабильном WS и активном эфире: **нет** устойчивого потока **12+ GET/мин** только из `live-broadcast`.
- UI по-прежнему показывает начало/конец эфира без перезагрузки.
- `npm run build -w web` без ошибок.

## Фаза B — Legacy `balance_updated` (medium)

**Цель:** не вызывать полный `GET /me` на каждый legacy-событие, если уже есть `me_update`.

**Шаги:**

1. **API:** найти все `publishBalanceUpdate` / события `balance_updated`; убедиться, что путь «изменение баланса» всегда шлёт `me_update` с нужным патчем (`buildMeEconomyPatch`).
2. **Web:** в `useRealtimeWebSocket.ts` для `balance_updated`: либо **no-op**, либо вызов **лёгкого** патча, если тело события позволяет; иначе один раз `refreshMe` — только как fallback.
3. Документировать в комментарии хука: `balance_updated` deprecated.

**Критерии:** меньше лишних `GET /me` при операциях, которые уже дают `me_update`; поведение баланса в шапке корректно.

---

## Фаза C — Dedupe `refreshMe` (medium)

**Цель:** параллельные вызовы не порождают гонки и лишние одинаковые запросы.

**Шаги:**

1. Вынести `refreshMe` в хук или модуль с **in-flight promise**: повторный вызов во время запроса возвращает тот же Promise (или последующий ждёт завершения и не стартует второй GET).
2. Опционально: `AbortController` для отмены устаревшего ответа (осторожно с `flushSync` в текущем `App`).

**Критерии:** быстрые двойные триггеры (таб + таймер) не дают двух успешных `/me` подряд без необходимости; UI не ломается.

---

## Фаза D — `watchLive`: убрать лишний `/me` (low)

**Цель:** после `POST /api/v1/live-broadcast/watch` не вызывать `onRefresh()`, если `patchMe` + приходящий `me_update` покрывают стрик и баланс.

**Шаги:**

1. Проверить ответ POST: есть ли поля для локального обновления без `/me`.
2. Убрать `await onRefresh()` из успешного пути или заменить на условный refresh только если WS отключён.

**Критерии:** один просмотр стрима не даёт лишнего `GET /me` при работающем realtime.

---

## Фаза E — Задания: `onRefresh` после claim (low / optional)

**Цель:** после `POST /tasks/:id/claim` полагаться на `me_update`, если сервер гарантирует пуш.

**Шаги:**

1. API: при успешном claim вызвать `publishBalanceUpdate` / `me_update` (если ещё не вызывается).
2. Web: убрать или сделать условным `onRefresh()` в `Tasks.tsx` при успешном claim.

---

## Фаза F — WebSocket reconnect (low)

**Шаги:** в `useRealtimeWebSocket` — экспоненциальный backoff перед повторным подключением, максимум N попыток; `onOpen` остаётся точкой синка.

**Критерии:** нет tight loop при падении сокета; после восстановления — один sync дропа/эфира как сейчас.
